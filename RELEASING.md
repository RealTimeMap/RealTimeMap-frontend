# Версии и релизы

Версию руками менять не нужно — её поднимает CI по сообщениям коммитов.

## Где живёт версия

**Источник правды — git-тег, а не `package.json`.**

В `package.json` стоит заглушка `0.0.0`, и она такой и остаётся: поле нужно только потому, что его требует npm-схема. Реальная версия подставляется при сборке — в вебе через `__APP_VERSION__` ([vite.config.ts](vite.config.ts)), в Android через `versionName`/`versionCode` ([build.gradle](android/app/build.gradle)). Оба берут её по одному правилу: переменная `APP_VERSION` → последний git-тег → `0.0.0`.

Сделано так, чтобы релиз не требовал коммита версии в `main`. Иначе `main` уходил бы вперёд на «chore(release)», а `develop` отставал, и его приходилось бы мержить обратно после каждого выпуска.

## Главное правило

**Релиз выпускается только при попадании коммитов в `main`.**

Работа в `develop` и любых других ветках ничего не выпускает — можно коммитить `feat` и `fix` сколько угодно. Момент релиза выбираете вы сами, когда мержите `develop` в `main`.

Что происходит при push в `main` ([.github/workflows/deploy.yml](.github/workflows/deploy.yml)):

1. `changelogen` смотрит коммиты с последнего тега и считает новую версию;
2. дописывает `CHANGELOG.md`, коммитит **только его** с `[skip ci]` и ставит тег `vX.Y.Z`;
3. собирает веб и APK, передавая версию через `APP_VERSION`;
4. создаёт GitHub Release, где описанием служит свежая секция changelog;
5. если ни один коммит не поднимает версию — **релиза не будет**, сборка просто пропускается.

Приложение сравнивает свою версию с тегом последнего релиза ([AppUpdate](src/components/02.features/AppUpdate/model/index.ts)) и предлагает обновиться.

## Текст в уведомлении об обновлении

Полный changelog уходит на страницу GitHub Release, а в уведомлении показывается короткая сводка ([summarizeRelease](src/components/02.features/AppUpdate/model/summarizeRelease.ts)). Она выбирает самый человеческий источник из трёх:

1. **заметки, написанные вами** — строка `Release-note:` в теле коммита;
2. темы `feat`-коммитов, если заметок не было;
3. счётчики по разделам, если и тем нет.

Заметка пишется в теле коммита и попадает в релиз автоматически:

```
feat(chat): оптимистичная отправка

Release-note: Чаты стали быстрее, сообщения не теряются при плохой связи
```

Пользователь увидит именно эту фразу. Без неё в уведомление уйдут технические темы коммитов вроде «Chip notification android live action» — понятные разработчику, но не тем, кто ставит обновление.

## Какой тип что делает

Тип коммита задаётся в [changelog.config.ts](changelog.config.ts), он же — источник списка для валидации [commitlint.config.ts](commitlint.config.ts).

| Тип        | Двигает версию | Раздел в CHANGELOG    |
| ---------- | -------------- | --------------------- |
| `feat`     | да             | 🚀 Функциональность   |
| `fix`      | да             | 🩹 Исправления        |
| `perf`     | да             | 🔥 Производительность |
| `refactor` | да             | 💅 Рефакторинг        |
| `upd`      | да             | ⬆️ Обновления         |
| `new`      | да             | 🆕 Новое              |
| `style`    | да             | 🎨 Стили              |
| `docs`     | **нет**        | 📖 Документация       |
| `build`    | **нет**        | 📦 Сборка             |
| `chore`    | **нет**        | 🏡 Разное             |
| `ci`       | **нет**        | 🤖 CI                 |
| `test`     | **нет**        | ✅ Тесты              |

Нижние пять попадают в changelog, но релиз сами по себе не запускают. Если нужно влить в `main` что-то инфраструктурное, не выпуская версию, — используйте их.

## Насколько вырастет версия

Пока мажорная часть равна нулю, semver считает API нестабильным и сдвигает всё на разряд вниз. При текущей `0.0.x`:

| Коммит            | Было → станет      |
| ----------------- | ------------------ |
| `fix(ui): ...`    | 0.0.11 → 0.0.12    |
| `feat(chat): ...` | 0.0.11 → 0.0.12    |
| `feat(api)!: ...` | 0.0.11 → **0.1.0** |

То есть **на `0.0.x` разницы между `feat` и `fix` нет** — обе дают патч. Она появится после выхода на `0.1.0`: тогда `feat` начнёт давать `0.2.0`, а `fix` — `0.1.1`. После `1.0.0` заработает полная схема, где ломающее изменение даёт `2.0.0`.

### Ломающие изменения

`!` после типа или scope помечает несовместимое изменение:

```
feat(api)!: сменил контракт отправки сообщений
```

Равнозначный вариант с пояснением — футер в теле коммита:

```
fix(api): поправил ответ history

BREAKING CHANGE: поле clientMessageId стало обязательным
```

Такие коммиты выносятся в CHANGELOG отдельной секцией наверху, а значит попадают в уведомление об обновлении — пользователь увидит предупреждение до установки.

## Как посмотреть, что выйдет, ничего не выпуская

Changelog за накопленные коммиты, без изменения файлов:

```bash
bunx changelogen
```

Если нужно увидеть и будущий номер версии — прогоните бамп локально и откатите:

```bash
bun run bump                      # меняет package.json и CHANGELOG.md
node -p "require('./package.json').version"
git checkout package.json && rm -f CHANGELOG.md
```

Откатывать обязательно: `package.json` должен оставаться с заглушкой `0.0.0`.

## Формат сообщений

Проверяется хуком `commit-msg` при каждом коммите:

```
тип(scope): описание
```

Scope обязателен: `fix: текст` не пройдёт, нужно `fix(ui): текст`. Регистр описания не проверяется — русские сообщения с заглавной буквы допустимы. Длина заголовка — до 100 символов.

Хук ставится через `postinstall`. Если репозиторий был склонирован раньше и хук не срабатывает:

```bash
bunx simple-git-hooks
```

## Версия Android

`versionName` и `versionCode` в [android/app/build.gradle](android/app/build.gradle) вычисляются при сборке из той же цепочки `APP_VERSION` → git-тег → `0.0.0`, править их руками не нужно. `versionCode` считается как `major * 10000 + minor * 100 + patch` — Android требует целое монотонно растущее число.

Локальная сборка APK без переменной возьмёт последний тег, достижимый из текущей ветки. На `develop` это может быть тег старее последнего релиза — для отладочной сборки не важно, а CI всегда передаёт версию явно.
